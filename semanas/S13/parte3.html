Miren la arquitectura del laboratorio. El estudiante es quien pregunta y quien revisa cada resultado. Opencode actúa como anfitrión MCP local. Recibe la pregunta, enumera herramientas y ordena la llamada. El servidor MCP vive en server.js dentro de la carpeta mcp caribemart. Ese programa expone las herramientas y lee los datos reales desde pedidos json. Todo corre en la misma computadora por stdio, sin red. La separación es pedagógica. Opencode no sabe nada de pedidos. Solo sabe hablar MCP. La lógica de negocio vive exclusivamente en su servidor.Esa separación también aclara roles en soporte y revisión. Si el servidor no responde, revisan el código de negocio. Si opencode no lo encuentra, revisan la configuración del anfitrión. Cada capa se depura por separado con evidencia propia. Esa disciplina docente ahorra discusiones largas en clase.
El esqueleto tiene solo dos dependencias. La primera es el SDK oficial de MCP para TypeScript, el paquete modelcontextprotocol sdk. Ese paquete trae el servidor, el transporte stdio y los tipos. La segunda es zod, una librería de validación que describe reglas en código. Su archivo package.json usará módulos nativos de Node con type module para importaciones limpias. Fíjense que no necesitan marco web ni base de datos externa. Un archivo JSON local basta para el laboratorio. La simplicidad es intencional. Menos piezas significan menos errores al empezar.La versión del SDK merece una nota breve. Hoy el paquete oficial de referencia es el de la serie uno punto treinta y dos. En su package.json usarán el nombre modelcontextprotocol sdk con zod. Copien las líneas exactas de la guía y no inventen nombres de paquetes. La guía ya trae el bloque verificado listo para pegar.
El esqueleto incluye una sola herramienta, consultar pedido. Su función es muy simple. Recibe el identificador, busca ese registro dentro del archivo pedidos json y devuelve un texto con el estado y el cliente. Si el pedido no existe, devuelve un mensaje claro de no encontrado en lugar de fallar. Fíjense en el diseño. El manejador es asíncrono y solo lee memoria local, así que responde rápido y sin efectos secundarios. Esa es la base segura. Ustedes luego agregarán las dos herramientas restantes siguiendo el mismo patrón exacto.El texto de salida debe ser útil para opencode y para ustedes. Incluye el identificador, el estado y el cliente sin adornos. Si el pedido no existe, el mensaje dice no encontrado con calma. Esa claridad evita que el modelo improvise una respuesta ante el silencio. Textos cortos y honestos rinden más en producción.
La validación ocurre antes de ejecutar código. Con zod declaramos que el identificador debe ser un entero positivo. El SDK genera automáticamente el JSON Schema que viaja en la descripción de la herramienta y usa esa misma regla para rechazar llamadas inválidas. Si el modelo envía texto, un número con decimales o un valor negativo, la llamada se detiene con error de parámetros y el manejador jamás toca los datos. Piensen en zod como la puerta de entrada. Todo lo que no cumple la regla se queda afuera. En crear pedido esa puerta será aún más estricta.La lista cerrada de estados merece atención especial. Solo acepten los valores que CaribeMart reconoce como válidos. Un texto libre como enviado hoy o urgente mañana rompería todos los filtros. En listar por estado usarán la misma lista en ambos lugares. Esa consistencia simple protege reportes y métricas futuras.
Después de crear los archivos ejecutan npm install dentro de la carpeta del servidor. Ese comando instala el SDK y zod en una carpeta local node modules. Luego el servidor no se ejecuta a mano como un servicio web. Opencode lo inicia cuando lo necesita por stdio. La regla de oro es no usar console log normal dentro del servidor. La salida estándar en stdio es el canal de mensajes MCP. Un log normal corrompe el JSON y rompe la conexión. Por eso usamos console error, que escribe por la salida de error sin tocar el protocolo.La carpeta node modules puede crecer bastante y eso es normal. No la suban al repositorio ni la compartan en zip. Cada compañero ejecuta npm install en su máquina y obtiene la misma estructura. En la entrega solo viajan server.js y package.json. Esa higiene mantiene el proyecto ligero y revisable.
El registro usa el formato vigente de opencode versión dos. Los servidores ya no cuelgan directamente de mcp. Ahora van bajo mcp servers con un nombre único. Para el laboratorio ese nombre será caribemart. El tipo es local, el comando es una lista con node y la ruta de server.js. El archivo opencode json debe quedar en la carpeta del proyecto, no en otra ubicación. Ojo con la lección de la semana doce. El formato viejo con enabled ya no aplica. Si copian ese ejemplo de Context7 sin actualizar, la conexión fallará. La guía de la actividad trae el bloque exacto listo para copiar.La ruta del comando debe coincidir con la carpeta real del proyecto. Si trabajan en C caribe lab siete, el resto del camino sigue esa base. Una sola letra cambiada rompe la conexión sin mensaje amable. Abran el Explorador y comparen letra por letra. La precisión en rutas es parte del criterio profesional.
Antes de preguntar nada, verifiquen la conexión. En PowerShell ejecuten opencode mcp list. Debe aparecer caribemart como conectado. Si aparece desconectado, paren y revisen. Las causas típicas son ruta incorrecta del servidor o nombre de archivo con extensión duplicada. Dentro de opencode también pueden escribir barra mcps para ver el estado y los registros. La regla es simple. Sin conectado verificado, ninguna prueba del modelo será válida. Dediquen dos minutos a esta verificación y se ahorrarán horas de errores.Ese comando también sirve para cambiar de proyecto sin perder el rastro. Cada carpeta con su opencode json tiene su propia conexión. El listado refleja la carpeta donde ejecutan PowerShell. Si no aparece caribemart, probablemente están en otra carpeta. Volver a la ruta correcta resuelve casi todos los casos.
Recorramos el flujo completo sin saltos. El estudiante pregunta por el estado del pedido número mil uno. Opencode envía la pregunta al modelo con la lista de herramientas. El modelo propone caribemart consultar pedido con el número mil uno. Opencode pasa esa propuesta a su servidor local. El servidor ejecuta, lee el JSON y devuelve la observación enviado. Opencode la entrega al modelo y el modelo responde en español con el dato verificado. Fíjense que en la pantalla de opencode verán el nombre completo de la herramienta. Esa línea es su evidencia más importante.El tiempo total del flujo debe ser corto en el laboratorio. Si tarda demasiado, revisen si abrieron muchos procesos a la vez. Un solo servidor local responde en milisegundos para datos pequeños. La lentitud casi siempre es red del modelo y no su servidor. No confundan esperas externas con errores locales.
Cuando pregunten en opencode, busquen una línea muy específica. La herramienta se nombra con el formato servidor guion bajo herramienta. En su caso será caribemart consultar pedido. Opencode mostrará también los argumentos enviados y el resultado recibido. Esa pantalla completa es la primera evidencia de la actividad. No basta con capturar la respuesta final del modelo. Deben mostrar la llamada misma, porque la llamada prueba que el modelo usó la herramienta. Tomen captura con el número mil uno visible y el estado enviado a la vista. Guárdenla con el nombre evidencia uno.La captura debe incluir la línea de la herramienta y el resultado. La respuesta final del modelo sola no prueba nada. Piensen en la rúbrica como un auditor que busca esa prueba. Sin la llamada visible, la evidencia no convence a nadie. Tomen tiempo para capturar bien cada una de las tres.
Ustedes agregarán dos herramientas más. La primera, listar pedidos por estado, solo lee. Recibe un estado de una lista cerrada, por ejemplo pendiente o enviado, y devuelve los pedidos que coinciden. La segunda, crear pedido, escribe en la base. Por eso exige validación completa. El cliente debe ser un texto no vacío, el total un número positivo y el estado uno de los valores permitidos. El servidor asigna el número nuevo y guarda el registro. Sigan el mismo patrón de consultar pedido. Esa repetición disciplinada es lo que evalúa la rúbrica.La confirmación humana en crear merece una repetición breve. Aunque la herramienta esté bien validada, ustedes aprueban antes de guardar. Ese hábito protege incluso contra planes equivocados del modelo. Piensen en aprobación como un acto profesional y no como trámite. En la próxima parte veremos por qué es innegociable.
Si algo falla, no depuren a ciegas dentro de opencode. La especificación ofrece el Inspector, un cliente de prueba oficial. Con ese comando abren una página donde ven las herramientas de su servidor y las llaman a mano con cualquier argumento. Es el lugar perfecto para probar un estado inválido y confirmar que zod lo rechaza. Úsenlo también para confirmar que crear pedido asigna un número nuevo sin duplicar. Cuando el Inspector responde bien, opencode casi seguro funcionará. Depurar por capas separadas ahorra mucho tiempo.El inspector también muestra el esquema generado por zod con claridad. Úsenlo para leer cómo el modelo ve su herramienta. Si la descripción es confusa, el modelo elegirá mal aunque el código funcione. Mejorar la descripción es mejorar la experiencia sin tocar lógica. Esa lección vale para cualquier interfaz futura.
Tres fallos concentran casi todos los problemas de arranque. El primero es una ruta errada en opencode json, donde el comando apunta a un archivo que no existe. El segundo es el clásico punto txt de Windows, donde el Bloc de notas guarda server.js punto txt y Node no lo encuentra. El tercero es olvidar npm install, con lo cual el SDK no está presente. Ante cualquier desconexión, revisen en ese orden. Abran la carpeta, confirmen el nombre exacto del archivo y ejecuten de nuevo la instalación. La guía de la actividad lista cada síntoma con su arreglo.La extensión punto txt merece recordar en cada Windows nuevo. El Bloc de notas simplificado oculta la extensión y engaña al estudiante. Activen la vista de extensiones en el Explorador antes de crear archivos. Esa pequeña configuración evita la mitad de los errores de arranque. Incluyan ese paso siempre en sus guías paso a paso.
