Entramos en el protocolo MCP. La sigla completa es Model Context Protocol, en español protocolo de contexto del modelo. La documentación oficial lo explica con una analogía que retengan. Igual que el puerto USB-C permite conectar cualquier dispositivo, MCP permite conectar cualquier aplicación de inteligencia artificial con cualquier sistema externo. Sin MCP cada cliente inventa su propio conector. Con MCP, el servidor expone herramientas, recursos y prompts con un formato único. En esta parte veremos quiénes participan, qué puede exponer cada servidor y por qué camino viajan los mensajes.Piensen en el beneficio práctico para un equipo pequeño. Sin estándar cada integración cuesta semanas enteras de desarrollo. Con estándar la tienda escribe su servidor una sola vez. Luego lo conecta en opencode o en otro cliente sin reescribir. Ese ahorro se acumula en cada proyecto nuevo de CaribeMart.
La arquitectura de MCP es cliente servidor, pero con nombres precisos. El anfitrión, host en inglés, es la aplicación de inteligencia artificial que coordina todo. Ejemplos reales son opencode o Visual Studio Code. Por cada servidor que conecta, el anfitrión crea un cliente MCP. Ese cliente mantiene una conexión dedicada con su servidor. El servidor MCP es el programa que provee el contexto. Puede vivir en la misma computadora por stdio o en un servicio remoto por HTTP. Un solo anfitrión puede tener varios clientes y cada uno habla con un servidor distinto.Esa distinción evita errores frecuentes de diseño. El anfitrión no ejecuta la herramienta y el servidor no decide solo. Cada uno protege su responsabilidad con registros claros. Cuando algo falla, saben exactamente dónde mirar. Esa claridad es esencial para depurar con rapidez en el laboratorio.
Todo servidor MCP ofrece tres primitivas y deben distinguirlas con total claridad. Las herramientas son funciones ejecutables que el modelo puede invocar para actuar, por ejemplo consultar un pedido o crear uno. Los recursos son fuentes de datos de solo lectura, como el contenido de un archivo o el esquema de la base de datos. Los prompts son plantillas reutilizables que guían el trabajo, por ejemplo un resumen de pedidos pendientes. Cada primitiva se descubre con su propia lista y se usa con su propio método. Confundirlas lleva a diseñar mal la seguridad.En la práctica diseñarán primero herramientas para actuar en CaribeMart. Los recursos y prompts completarán después el contexto. Esa prioridad evita sobreconstruir datos pasivos sin uso real. Empiecen por la acción que el estudiante necesita hoy. El resto evoluciona con evidencia de uso.
Detallamos las herramientas MCP. Son la primitiva más poderosa porque permiten escribir en bases de datos, llamar servicios y modificar archivos. El modelo las descubre con el método tools list y las ejecuta con tools call. La documentación insiste en que son controladas por el modelo, pero eso no significa control total. La aplicación anfitriona puede mostrar las herramientas disponibles, pedir aprobación antes de ejecutar y registrar cada llamada. Para CaribeMart esto significa que crear pedido exigirá confirmación, mientras que consultar pedido podrá ser automático. El grado de permiso se diseña herramienta por herramienta.La aprobación no debe ser un obstáculo ciego para todo. Lean bien cada herramienta y clasifiquen su riesgo real. Una consulta de lectura puede aprobarse sola sin fricción. Una escritura que crea pedidos siempre pide tu visto bueno. Esa calibración mantiene la ayuda rápida sin perder control.
Los recursos son el contraste perfecto con las herramientas. Mientras las herramientas actúan, los recursos solo informan. Cada recurso tiene un identificador único llamado URI, por ejemplo pedidos esquema, y declara su tipo MIME. La aplicación anfitriona decide cómo usarlos. Puede pasar todo el contenido al modelo, buscar un fragmento relevante o mostrar una vista previa al usuario. La clave es que el modelo no los invoca por sí solo. La aplicación los recupera y los ofrece como contexto. Para CaribeMart, el esquema de pedidos y la política de devoluciones serían recursos típicos.Esa flexibilidad de la aplicación evita depender del modelo para cada lectura. Ustedes eligen qué contexto pasa y en qué momento. Si el recurso es grande, seleccionan solo el fragmento útil. Así controlan costos de tokens y latencia. La aplicación siempre decide la dieta de información del modelo.
Los prompts completan el trío. Son plantillas reutilizables que el servidor publica para guiar una tarea completa. A diferencia de las herramientas, nadie los dispara automáticamente. El usuario los elige explícitamente, muchas veces con una barra diagonal en opencode. Al elegirlos, entrega los argumentos y el servidor devuelve la instrucción estructurada que combina herramientas y recursos. Piensen en un prompt de resumen de pedidos pendientes. Esa plantilla indicaría qué herramienta llamar y cómo redactar la salida. Los prompts dan consistencia a los flujos repetidos en CaribeMart.La plantilla también documenta el flujo esperado para nuevos compañeros. Quien lee el prompt entiende qué herramientas combina y en qué orden. Esa trazabilidad ayuda a mantener soporte durante meses. No dejen prompts escondidos sin descripción clara en el servidor.
El protocolo organiza el trabajo en intercambios muy claros. Primero el cliente descubre qué versiones y capacidades soporta el servidor. Segundo lista las herramientas disponibles con su nombre, descripción y esquema de entrada. Tercero llama una herramienta concreta con sus argumentos y recibe el resultado. Todo mensaje usa JSON RPC, es decir, un objeto JSON con versión, método y resultado. Esa uniformidad permite que cualquier cliente hable con cualquier servidor. Fíjense que el descubrimiento elimina sorpresas. Nadie debe intentar una herramienta que el servidor no anunció.Las versiones importan para no romper clientes actuales. El cliente y el servidor negocian qué revisión hablan. Si uno no entiende la versión del otro, falla con claridad. Esa regla evita mensajes silenciosos que nadie sabe interpretar. En el laboratorio verán esa negociación en los registros del inspector.
El transporte stdio es el más simple y el que usarán en el laboratorio. Usa la entrada y salida estándar entre dos procesos de la misma máquina. Opencode inicia el programa Node y los mensajes JSON fluyen por una tubería interna. No hay red, no hay puerto abierto ni autenticación complicada. La documentación advierte una regla crítica. Nunca escriban mensajes normales por la salida estándar del servidor porque corrompen el protocolo. Todos los registros deben ir por la salida de error. Por eso en Node usaremos console error y jamás console log para mensajes del servidor.La simplicidad de stdio reduce superficie de ataque en clase. No hay puertos abiertos ni claves en la red local. El único riesgo es el archivo en disco, que ustedes controlan. Por eso el laboratorio exige stdio y no un servidor web. Aprendan lo esencial antes de escalar a remoto.
El segundo transporte es Streamable HTTP, diseñado para servidores remotos. Permite que muchos clientes se conecten al mismo servidor por internet usando HTTP cifrado. La especificación recomienda OAuth para obtener tokens de autenticación. Context7, que conectamos en la semana doce, es un ejemplo real de servidor remoto. Comparen con stdio. Stdio es local y simple. HTTP es remoto y escalable. Los mensajes JSON RPC son los mismos en ambos casos. Solo cambia el canal. Para CaribeMart empezaremos en local con stdio y dejaremos el diseño remoto para producción.En producción el transporte remoto exige credenciales y registros sólidos. Un token filtrado puede exponer todas las herramientas del servidor. Por eso OAuth y claves rotadas son obligatorios fuera del laboratorio. No expongan un servidor stdio como si fuera remoto sin adaptarlo. Cada transporte tiene su propio nivel de exigencia.
No confundan una interfaz de programación de aplicaciones REST con MCP. REST expone recursos del servidor, como el pedido número mil uno, y la aplicación decide cuándo pedirlos. MCP expone herramientas con esquemas que el modelo lee y elige en el momento adecuado. REST habla de recursos. MCP habla de acciones para el modelo. Ambos usan JSON y HTTP o tuberías, pero su intención es distinta. REST conecta programas entre sí. MCP conecta un modelo con capacidades reales. En CaribeMart ustedes seguiremos usando REST para el servicio de pedidos y MCP encima para exponerlo a opencode.La coexistencia es normal en sistemas reales bien diseñados. El servicio de pedidos seguirá hablando REST con otros sistemas. Encima expondrán un servidor MCP para opencode. Así cada cliente usa el idioma que necesita sin romper lo existente. Esa arquitectura por capas protege la inversión ya hecha en CaribeMart.
Segundo mini reto. Pausen el video y clasifiquen tres tareas de CaribeMart. Caso A, leer el esquema de pedidos sin cambiar nada. Caso B, crear un pedido nuevo que escribe en la base. Caso C, un resumen guiado de pendientes que siempre sigue los mismos pasos. Fin de la pausa. La respuesta es recurso para A, herramienta para B y prompt para C. Fíjense que el criterio no es la dificultad. Es la naturaleza de la acción. Leer es recurso, actuar es herramienta y guiar es prompt. Si clasificaron así, van por buen camino.Esa clasificación se practica en cada diseño nuevo que hagan. Antes de escribir código, pregunten si leen, actúan o guían. La respuesta define la primitiva correcta y su control. Si dudan, elijan la opción más leída y menos potente. La prudencia inicial evita incidentes costosos después.
Context7 no es un juguete. La documentación oficial describe un ecosistema amplio con clientes como Claude, ChatGPT, Visual Studio Code y herramientas de desarrollo que ya soportan MCP. Eso significa que un servidor bien escrito funciona en muchos lugares sin cambios. Los ejemplos oficiales incluyen servidores de archivos, bases de datos y monitoreo como Sentry. La lección para ustedes es clara. Si aprenden a construir un servidor MCP correcto, ganan una habilidad portable. No dependen de una sola aplicación ni de un solo proveedor. Esa portabilidad es el valor real del estándar.La lista de clientes compatibles sigue creciendo cada mes. Eso valida la apuesta por un estándar abierto y documentado. Su servidor de hoy funcionará con clientes futuros sin cambios. Esa longevidad es un argumento fuerte para invertir tiempo en aprender. No gasten esfuerzo en conectores desechables de un solo producto.
Todo mensaje MCP viaja en un sobre JSON RPC con tres piezas obligatorias. La versión del protocolo, el nombre del método y los parámetros enviados. La respuesta copia el identificador original y trae el resultado o un error con código claro. Esa disciplina permite correlacionar cada petición con su respuesta sin ninguna ambigüedad. Las notificaciones son mensajes sin respuesta esperada, por ejemplo un aviso de lista cambiada. Fíjense en la utilidad práctica para depurar. Cuando revisen registros, leerán esos tres campos y sabrán si falló el método, los parámetros o el servidor. Esa claridad ahorra horas de adivinación en el laboratorio. Piensen además en la compatibilidad entre versiones diferentes. Si el cliente habla una revisión vieja y el servidor una nueva, el sobre lo revela con claridad. Esa negociación ordenada evita conexiones a medias que nadie entiende. En la próxima parte verán esos mensajes en el inspector al probar.
