Laboratorio 3: Contenedores y Docker Hub

Del primer contenedor a una imagen publicada en Docker Hub con etiquetas inmutables, una prueba de portabilidad real y un reto multi-contenedor — todo en una estación propia que se crea y se destruye contigo

Docente: Ing. Rodolfo Cañas Cervantes Universidad de la Costa (CUC) 2026-2 · Ponderación: por definir

Este laboratorio continúa el Lab 1. Allá construiste una imagen y la publicaste en un registro privado de tu sesión. Aquí vas a hacer lo mismo pero en Docker Hub: el registro público que usan todas las empresas para distribuir sus imágenes, y que es el paso previo a desplegar en la nube.

Van a ser diez pasos, y cada uno deja evidencia que revisar comprueba solo:

  1. Preparas tu cuenta de Docker Hub y tu estación.
  2. Corres tu primer contenedor y publicas su puerto.
  3. Escribes tu propio Dockerfile y construyes una imagen.
  4. Comprendes las capas y los tags de build.
  5. Publicas en Docker Hub.
  6. Publicas una versión 2 con etiquetas inmutables.
  7. Pruebas que la imagen es portable en un entorno limpio.
  8. Levantas un reto multi-contenedor.
  9. Ejecutas revisar y la evidencia queda registrada.

Lo que NO se hace aquí: no usas ninguna plataforma online tipo Play with Docker. Tu Docker es real, vive en tu estación y se borra contigo. La diferencia con esa plataforma es que lo que publicas en Docker Hub sí se queda: es tu cuenta y tu repositorio.

0

Paso 0 — Tu cuenta y tu estación

0.1 · Entra a tu estación

  1. Entra en https://labs.proyectoasur.org con tus credenciales.
  2. Busca el Lab 3 — Contenedores y Docker Hub y pulsa Iniciar lab.
  3. Cuando diga Entrar, ábrelo: verás tu terminal y, al correr algo en el puerto 8080, la pestaña Mi aplicación.

0.2 · Dile a la estación quién eres

La plataforma nunca guarda ni registra tu token de Docker Hub: lo escribes tú en tu terminal y se borra con la estación. Lo único que necesita saber el validador es tu usuario, para poder comprobar en Docker Hub que tus etiquetas existen.

mi-espacio
echo 'tu-usuario-de-dockerhub' > /workspace/.dockerhub-user
export USUARIO=$(cat /workspace/.dockerhub-user)
echo "USUARIO=$USUARIO"

0.3 · Autentícate contra Docker Hub

docker login
# Username: tu-usuario-de-dockerhub
# Password: tu access token de Docker Hub (Settings → Security → New Access Token)
A

Paso 1 — Tu primer contenedor

docker run --rm hello-world

La opción --rm borra el contenedor al salir: no queda nada ocupando disco. Comprueba que no quedó ninguno:

docker ps -a
2
B

Paso 2 — Un servidor web con puertos

Un contenedor sin publicar su puerto es un mundo cerrado. Con -p lo abres hacia el exterior.

docker run -d --name web -p 8080:80 nginx:1.27-alpine

Comprueba desde dentro de tu estación:

docker ps --filter name=web
curl -s http://127.0.0.1:8080 | head -5
2

Y en el navegador: tu sesión tiene una pestaña Mi aplicación que muestra exactamente lo que hay en el puerto 8080 de tu estación.

B.1 · Entra al contenedor

docker exec -it web sh
cat /usr/share/nginx/html/index.html
exit
3

Dentro, mira qué hay en el índice de nginx y sálese con exit.

C

Paso 3 — Tu propio Dockerfile

En /workspace/app tienes el código de partida de una aplicación Node con su Dockerfile. Léelos:

cd /workspace/app
cat server.js
cat Dockerfile

Construye tu imagen:

cd /workspace/app
# libera el puerto 8080, que ocupaba el contenedor web del paso 2
docker rm -f web
docker build -t mi-app:1.0.0 .
2
D

Paso 4 — Builds con capas y con tags

Cada instrucción del Dockerfile es una capa. Si cambias solo el server.js, el npm install se sirve del cache:

# toca server.js (cambia un mensaje) y vuelve a construir
docker build -t mi-app:1.0.0 .
# mira las líneas CACHED

Fíjate en CACHED en la salida. Ahora etiqueta lo mismo con varias referencias:

docker tag mi-app:1.0.0 mi-app:latest
docker images
2

Las etiquetas son punteros: mover latest no borra nada, solo cambia a dónde apunta. Por eso en producción se usan etiquetas inmutables (un número de versión que nunca se reutiliza) y latest solo para desarrollo.

E

Paso 5 — Publica en Docker Hub

docker tag mi-app:1.0.0 $USUARIO/mi-app:v1
docker push $USUARIO/mi-app:v1

En Docker Hub verás el repositorio mi-app con la etiqueta v1. Anota el digest que imprime el push: lo vas a comparar después.

Tu token no sale de tu terminal. La plataforma no lo ve, no lo guarda y no lo registra. Si te equivocas, revócalo en Docker Hub y genera otro.

F

Paso 6 — Versión 2 con etiquetas inmutables

Cambia algo de la app (un mensaje, un campo en /salud) y construye la versión 2:

# cambia algo en server.js
docker build -t mi-app:2.0.0 .
docker tag  mi-app:2.0.0 $USUARIO/mi-app:v2
docker push $USUARIO/mi-app:v2

Compara los digests de v1 y v2:

docker inspect -f '{{.Id}}' mi-app:1.0.0
docker inspect -f '{{.Id}}' mi-app:2.0.0
2

Deben ser distintos. Si fueran iguales, habrías publicado dos etiquetas apuntando a la misma imagen: eso es justamente lo que no hay que hacer.

G

Paso 7 — Prueba de portabilidad

La prueba real de que tu imagen sirve para algo es que otra persona pueda descargarla y correrla sin tu código. Simula ese entorno limpio:

docker rmi -f $USUARIO/mi-app:v2 mi-app:2.0.0
docker pull $USUARIO/mi-app:v2
docker run -d --rm --name portabilidad -p 18080:3000 $USUARIO/mi-app:v2
curl -s http://127.0.0.1:18080/salud
docker rm -f portabilidad

Has borrado tu copia local, la has vuelto a descargar desde el registro y ha arrancado en un contenedor nuevo. Eso es exactamente lo que pasa cuando despliegas en la nube.

H

Paso 8 — Reto multi-contenedor

Las aplicaciones reales no van solas: hay un servicio de datos, otro de caché, otro de colas. Aquí tienes un docker-compose.yml que levanta tu app junto a un servicio de datos.

cd /workspace/app
cat docker-compose.yml
docker compose up -d --build

Comprueba que la app habla con el servicio de datos:

curl -s http://127.0.0.1:8080/datos
2

Sube /datos varias veces: el contador lo lleva el otro contenedor. Mira los logs de ambos:

curl -s http://127.0.0.1:8080/datos
docker compose logs --tail 20
3
I

Paso 9 — Entregable

El entregable es la evidencia registrada por la plataforma. Ejecuta el validador:

revisar

Comprueba cinco cosas:

CriterioQué valida
Etiqueta v1 publicadaQue v1 existe en tu cuenta de Docker Hub
Etiqueta v2 con digest distintoQue v2 existe y su digest no es el de v1 (etiquetas inmutables)
El contenedor respondeQue la app responde HTTP 200 y se ve en la vista web de la sesión
PortabilidadQue la imagen publicada se descarga y corre en un entorno limpio
Reto multi-contenedorQue el compose está en marcha y /datos responde desde el servicio de datos
?

Solución de problemas

SíntomaCausa probableQué hacer
docker push falla con denied No hiciste login, o el repositorio es de otra cuenta docker login y comprueba que la imagen se llama TU-USUARIO/mi-app
El push es muy lento o falla con toomanyrequests Cuota anónima de Docker Hub por IP compartida Espera unos minutos. Las descargas pasan por el caché del servidor, pero el push usa tu cuenta y no tiene esa cuota
revisar no ve mis etiquetas No guardaste tu usuario, o publicaste con otro nombre cat /workspace/.dockerhub-user y comprueba en Docker Hub que el repositorio se llama TU-USUARIO/mi-app
v1 y v2 tienen el mismo digest Publicaste dos etiquetas sin cambiar nada Cambia el código, reconstruye y vuelve a publicar v2
El compose no levanta Falta el servicio datos o el nombre no coincide docker compose ps y docker compose logs
La vista web del navegador está en blanco Tu app no escucha en el puerto 8080 Arranca con -p 8080:3000 y comprueba curl 127.0.0.1:8080/salud

Checklist antes de entregar
