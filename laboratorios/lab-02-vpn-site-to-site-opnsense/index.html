Laboratorio 2 · Unidad 1 — Redes e interconectividad

VPN Site-to-Site entre dos OPNsense:
WordPress con base de datos remota

Dos firewalls, dos redes privadas, un túnel cifrado — y una aplicación que no sabe que su base de datos está "en el otro lado del mundo"

Curso: Integración de Soluciones para Plataformas Cloud — Ingeniería de Sistemas
Docente: Ing. Rodolfo Cañas Cervantes · Universidad de la Costa (CUC) · 2026-2
Duración estimada: 120 minutos  ·  Modalidad: VirtualBox local (4 VMs)  ·  Nivel: intermedio
Tipo: laboratorio práctico complementario — sin nota, para profundizar lo visto en clase

OBJETIVOS Qué vas a aprender

Al terminar este laboratorio serás capaz de:

  • Desplegar dos firewalls OPNsense virtualizados e interconectar sus redes privadas mediante una VPN site-to-site WireGuard.
  • Administrarlos desde el navegador y la terminal de los propios servidores del lab — sin instalar un solo sistema operativo.
  • Migrar el DHCP del dhcpd clásico a Kea, escribiendo también su configuración JSON nativa.
  • Separar capas de una aplicación real: WordPress (web/app) en un sitio y MariaDB (datos) en otro, comunicándose exclusivamente por el túnel.
  • Diagnosticar problemas de red con tcpdump, tablas de estados pf y filterlog — la metodología que usamos cuando las cosas se rompen de verdad.
Todo lo documentado aquí fue ejecutado y validado en un entorno real antes de escribirse. Cada comando funcionó; cada incidente descrito ocurrió de verdad.

Redes en VirtualBox — mapeo exacto

En VirtualBox: Archivo → Herramientas → Administrador de red → NAT Networks → Crear la red WANLAB con prefijo 172.10.20.0/24 y DHCP activado. Las Internal Networks LAN-A y LAN-B se escriben directo en el adaptador de cada VM.
El error más común del lab: conectar los dos servers a la MISMA internal network "por si acaso". Si LAN-A y LAN-B se tocan, la VPN pierde todo el sentido y las pruebas darán falsos positivos.

PARTE A Firewalls: instalación y acceso de administración (~25 min)

A.1 — Instalar OPNsense en ambas VMs

  1. Arranca desde la ISO → login installer / password opnsense.
  2. Acepta defaults: teclado, ZFS stripe (o UFS, indistinto en lab), disco completo.
  3. Al terminar: apaga, retira la ISO, arranca desde disco.
  4. Credenciales de consola: root / opnsense.

A.2 — Asignar interfaces y LAN (lo ÚNICO que se digita en consola)

Opción 1) Assign Interfaces
  LAN  → em1   (Adapter 2, la internal network)
  WAN  → em0   (Adapter 1, la NAT network)
Opción 2) Set interface(s) IP address → LAN
  → DHCP propio: NO
  → IP: 10.0.0.1/24   (Router-A)
        20.0.0.1/24   (Router-B)
  → IPv6: ninguno (Enter)
  → ¿Habilitar DHCP server en LAN? SÍ   ← temporal; lo migramos a Kea en la Parte B
     Rango: 10.0.0.100 - 10.0.0.200    (Router-A)
            20.0.0.100 - 20.0.0.200    (Router-B)

La WAN queda por DHCP de la propia NAT Network (recibirá alguna 172.10.20.x). Anótala — la necesitas para el Endpoint del túnel en la Parte C.

Si inviertes WAN/LAN, el lab entero se comporta raro. Verifica siempre con la opción 1 que LAN sea em1. Si tu versión de OPNsense ya no ofrece habilitar DHCP desde la consola, dale al server una IP temporal estática (10.0.0.10/24 gw 10.0.0.1) desde su applet de red y salta directo a la Parte B.

PARTE B Migración a Kea DHCP: del dhcpd clásico al moderno (~15 min)

El DHCP que habilitaste en la consola es el clásico (ISC dhcpd, retirado por ISC). OPNsense moderno usa Kea — aquí lo migramos como se hace en producción. Dos caminos:

Camino GUI (recomendado para empezar)

Services → Kea DHCP → Dhcpv4 → Subnets → +Add
Subnet 10.0.0.0/24, pool .100-.200, router 10.0.0.1, DNS 8.8.8.8,1.1.1.1
Luego: General → Enable, y desmarca el ISC viejo si aparece.

Camino JSON (lo que hicimos en producción)

Escribir /usr/local/etc/kea/kea-dhcp4.conf directo por SSH y service kea restart. Bloques completos abajo, para ambos routers.

B.1 — Configuración JSON completa (Router-A)

cat > /usr/local/etc/kea/kea-dhcp4.conf <<'KEA'
{
  "Dhcp4": {
    "interfaces-config": { "interfaces": ["em1"] },
    "control-socket": { "socket-type": "unix",
                        "socket-name": "/var/run/kea/kea4-ctrl-socket" },
    "lease-database": { "type": "memfile",
                        "name": "/var/db/kea/kea-leases4.csv", "persist": true },
    "valid-lifetime": 7200, "renew-timer": 1800, "rebind-timer": 3600,
    "subnet4": [ {
      "id": 1,                          // ← obligatorio desde Kea 3.0
      "subnet": "10.0.0.0/24",
      "pools": [ { "pool": "10.0.0.100 - 10.0.0.200" } ],
      "option-data": [
        { "name": "routers",             "data": "10.0.0.1" },
        { "name": "domain-name-servers", "data": "8.8.8.8, 1.1.1.1" }
      ]
    } ],
    "loggers": [ { "name": "kea-dhcp4",
      "output-options": [ { "output": "/var/log/kea/kea-dhcp4.log" } ],
      "severity": "INFO" } ]
  }
}
KEA
service kea restart

PARTE C El túnel WireGuard site-to-site (~35 min)

C.1 — Generar las claves (SSH en cada router)

# ROUTER-A
wg genkey | tee /tmp/priv_a | wg pubkey > /tmp/pub_a
cat /tmp/pub_a        # ← cópiala al portapapeles: viaja a ROUTER-B

# ROUTER-B
wg genkey | tee /tmp/priv_b | wg pubkey > /tmp/pub_b
cat /tmp/pub_b        # ← cópiala al portapapeles: viaja a ROUTER-A

El portapapeles bidireccional pasa la clave de una VM a la otra (VM → host → VM): copia en la terminal de SERVER-A, pega en la terminal de SERVER-B.

Nunca compartas PrivateKey en chats, capturas o repositorios. Solo las PÚBLICAS cruzan equipos.

C.2 — Configuración completa (Router-A)

La privada se inyecta sola con $(cat /tmp/priv_a); lo único que pegas a mano es la pública del peer, donde dice PEGA_AQUI_PUB_B:

mkdir -p /usr/local/etc/wireguard
cat > /usr/local/etc/wireguard/wg0.conf <<WG
[Interface]
PrivateKey = $(cat /tmp/priv_a)
ListenPort = 51820

[Peer]
PublicKey = PEGA_AQUI_PUB_B
Endpoint = 172.10.20.128:51820
AllowedIPs = 20.0.0.0/24, 10.99.0.2/32
PersistentKeepalive = 25
WG
chmod 600 /usr/local/etc/wireguard/wg0.conf
cat /usr/local/etc/wireguard/wg0.conf   # verifica: privada visible + pública del peer correcta

C.3 — Configuración completa (Router-B) — íntegra, sin "espejo"

mkdir -p /usr/local/etc/wireguard
cat > /usr/local/etc/wireguard/wg0.conf <<WG
[Interface]
PrivateKey = $(cat /tmp/priv_b)
ListenPort = 51820

[Peer]
PublicKey = PEGA_AQUI_PUB_A
Endpoint = 172.10.20.224:51820
AllowedIPs = 10.0.0.0/24, 10.99.0.1/32
PersistentKeepalive = 25
WG
chmod 600 /usr/local/etc/wireguard/wg0.conf
cat /usr/local/etc/wireguard/wg0.conf

C.4 — Activación y reglas firewall sobre wg0 (¡sin esto no pasa nada!)

# ROUTER-A (SSH):
ifconfig wg0 create name wg0
wg syncconf wg0 /usr/local/etc/wireguard/wg0.conf
ifconfig wg0 inet 10.99.0.1/30 alias
ifconfig wg0 up
route -n add -net 20.0.0.0/24 -interface wg0

# ROUTER-B (SSH):
ifconfig wg0 create name wg0
wg syncconf wg0 /usr/local/etc/wireguard/wg0.conf
ifconfig wg0 inet 10.99.0.2/30 alias
ifconfig wg0 up
route -n add -net 10.0.0.0/24 -interface wg0

Ahora las reglas, desde el navegador del server de cada sitio:

  1. Interfaces → Assignments → + agrega wg0 → habilítala con nombre WGVPN (sin configuración IP, ya la tiene) → Save.
  2. Firewall → Rules → WGVPN → + (en cada router): pass · IPv4 · any · Source = red LAN remota (A: 20.0.0.0/24 · B: 10.0.0.0/24) · Destination = any. Repite al revés: Source any → Destination red LAN remota.
  3. Firewall → Rules → WAN → + (en cada router — sin ella, NINGÚN paquete del túnel entra): pass · IPv4 · UDP · Source = IP WAN del peer (A: 172.10.20.128 · B: 172.10.20.224) · Destination = This Firewall · Puerto = 51820. Luego edítala → Display Advanced → desmarca "Reply-to" → Save → Apply.
Lo del reply-to no es superstición: OPNsense agrega reply-to (gateway WAN) a las reglas WAN y las respuestas salen forzadas por el gateway aunque hayan entrado por otro camino (ruteo asimétrico). En producción nos costó dos lockouts — es el incidente #2 de la sección Troubleshoot.

C.5 — Validación del túnel

wg show                     # latest handshake debe ser reciente (< 25s con keepalive)
ping -S 10.0.0.1 20.0.0.101 # ping LAN-A → Server-B cruzando el túnel (-S fija origen)
El ping SIN -S entre routers usa la IP del túnel (10.99.0.x) — si tus reglas solo cubren las redes LAN, ese ping fallará aunque el túnel esté perfecto. No te engañes a ti mismo: prueba siempre con IPs reales de servidor.

PARTE D MariaDB remoto + WordPress (~35 min)

D.1 — SERVER-B: la base de datos

sudo apt update && sudo apt install -y mariadb-server

# escuchar en todas las interfaces (el tráfico llega por la LAN)
sudo sed -i 's/^bind-address.*/bind-address = 0.0.0.0/' \
     /etc/mysql/mariadb.conf.d/50-server.cnf
sudo systemctl enable --now mariadb && sudo systemctl restart mariadb

# base de datos y usuario SOLO para la red remota
sudo mysql -e "CREATE DATABASE wordpress CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
sudo mysql -e "CREATE USER 'wpuser'@'10.0.0.%' IDENTIFIED BY 'WPLab2026!';"
sudo mysql -e "GRANT ALL PRIVILEGES ON wordpress.* TO 'wpuser'@'10.0.0.%';"
sudo mysql -e "FLUSH PRIVILEGES;"
ss -tln | grep 3306      → LISTEN 0.0.0.0:3306 ✓
'wpuser'@'10.0.0.%' significa "este usuario solo existe si viene desde la red del sitio A". Aunque alguien abriera el 3306 hacia internet, no tendría usuario válido. Defensa en profundidad: firewall + bind + grants.

PARTE E Validación final y evidencias (~15 min)

E.1 — Checklist de evidencias para tu auto-check

  • Captura de wg show en AMBOS routers mostrando handshake reciente y transfer > 0
  • Ping cruzado entre servers: ping -c3 20.0.0.101 desde SERVER-A y viceversa
  • Salida de SHOW TABLES; desde SERVER-A contra la IP remota (mysql -h 20.0.0.101 -u wpuser -p'WPLab2026!' wordpress)
  • Captura del navegador de SERVER-A cargando http://10.0.0.101/wordpress/
  • (Nivel pro) tcpdump en Router-B demostrando que el puerto 3306 llega por wg0, no por em0

E.2 — Prueba negativa (demuestra que la dependencia es real)

# en ROUTER-B, baja el túnel:
ifconfig wg0 down
# en SERVER-A, refresca el sitio → error "Error establishing a database connection" ✓
# sube el túnel:
ifconfig wg0 up    # keepalive re-negocia solo

Si tu app sigue funcionando sin túnel, tu demo no demuestra nada — esta prueba negativa es la que convierte una captura bonita en evidencia científica.

TROUBLESHOOT Los 6 incidentes que vivimos en producción — y cómo se diagnostican

Estos NO son hipotéticos: ocurrieron construyendo esta misma demo. Si algo falla, busca tu síntoma aquí — el método importa más que la respuesta.

#1 — Pierdo SSH al habilitar el firewall

SíntomaSSH muere justo tras aplicar reglas nuevas
CausaReglas con origen restringido a la red WAN local, administrando desde otra subred
Diagnóstico¿El SYN llega? (tcpdump) ¿Qué regla lo procesa? (contadores pfctl -vvsr)
Fixsource = any o incluir tu subred admin · sesión vieja abierta como cuerda de seguridad

#2 — Reglas correctas pero sin retorno (reply-to)

Síntomatcpdump ve los SYNs llegar; pf no crea estados ni responde; todo "muere en silencio"
CausaOPNsense agrega reply-to (em0 gateway) a las reglas WAN → las respuestas salen forzadas por el gateway WAN aunque entraran por otro camino (ruteo asimétrico)
DiagnósticoContadores de la regla suben pero Packets=0 · filterlog vacío para ese flujo · pfctl -sr muestra el reply-to clavado
FixEditar cada regla WAN → avanzado → deshabilitar reply-to

#3 — La IP estática del firewall "revierte sola"

SíntomaLa LAN del firewall cambia a una IP del pool DHCP sin que nadie la toque
CausaProceso dhclient residual de una configuración previa, relanzado por ciclos de interfaces
Diagnósticops aux | grep dhclient + leases del propio Kea mostrando hostname del router
FixMatar dhclient, limpiar /var/etc/dhclient.*.conf, re-fijar IP y verificarla tras cada reload

#4 — apt dice "network unreachable" pero el internet funciona

Síntomaapt update falla en los servers; ping a IPs públicas tampoco
CausaNO era el cliente: el gateway había perdido su ruta default y respondía ICMP host-unreachable a cada SYN
Diagnósticotcpdump en la LAN del gateway: ves SYNs correctos y respuestas ICMP-unreachable generadas POR EL ROUTER · netstat -rn | grep default
Fixroute add default <gw> + persistir el gateway en config.xml
Método general: captura en AMBOS extremos del enlace sospechoso. Lo que entra y no sale localiza el problema en un solo dispositivo.

#5 — Kea rechaza la configuración completa

Síntomakea-dhcp4 no arranca; errores de schema en el log
CausaKea 3.0 endureció validaciones: id obligatorio, paths de socket/log restringidos
Fixid numérico por subnet · socket bajo /var/run/kea · logs bajo /var/log/kea

#6 — El port forward "no funciona" aunque pf parece bien configurado

SíntomaRDR activo, regla pass presente, contadores evaluando… cero conexiones y cero estados
CausaTras el redirect, el paquete tiene destino POST-NAT (10.0.0.101) y la regla pass solo cubría la IP virtual (.230) → cae al bloqueo default. La GUI genera esa regla asociada automáticamente; manualmente hay que crearla aparte.
Diagnóstico estrella/var/log/filter/latest.log: el paquete aparece YA TRADUCIDO siendo bloqueado. El log te muestra el paquete tal como pf lo ve después del NAT.
FixSegunda regla pass contra el destino post-NAT (asociada al rdr)
Lección transversal: cuando pf "ignora" paquetes, la respuesta casi siempre está en el filterlog o en los contadores por-regla — nunca en adivinar más reglas.

AUTO-CHECK ¿Dominas esto? — verificación libre, sin nota

Este lab es complementario: nada se entrega ni se califica. Pero si puedes tachar esta lista completa, tienes un nivel de redes/firewalls que muchos ingenieros senior no tienen.

  • Explicar SIN mirar la guía por qué las reglas WAN necesitan disablereplyto
  • Túnel arriba: wg show con handshake reciente y transfer > 0 en ambos routers
  • Ping cruzado entre LANs usando IPs de servidor (no las del túnel)
  • WordPress instalado y creando tablas en la BD del OTRO sitio — SHOW TABLES desde ServerA
  • Prueba negativa: bajar wg0 → WordPress falla → subir → funciona. Sabes explicar por qué eso demuestra la dependencia
  • Sabes decir qué protocolo/puerto viaja cifrado dentro de qué otro (3306/TCP dentro de 51820/UDP)
Reto adicional si quieres más: agrega un tercer sitio (ROUTER-C, red 30.0.0.0/24) al túnel hub-and-spoke, o sustituye WireGuard por IPsec IKEv2 y compara overhead con iperf3.

Anexo G — ¿Por qué no usamos el plugin os-wireguard? 
Tres quirks reales que nos encontramos en producción:

1. El campo <interface> del server DEBE contener el nombre del dispositivo (wg0);
   vacío = no hace nada.
2. configctl wireguard configure sin UUID no ejecuta nada: hay que invocar
   php /usr/local/opnsense/scripts/wireguard/wg-service-control.php restart <uuid>
3. El script espera que otro proceso genere /usr/local/etc/wireguard/wg0.conf
   (render de templates que nunca se dispara por configd) → por eso lo escribimos a mano.

Además: la activación manual de la Parte C.4 NO sobrevive un reboot (es un lab).
Si quieres persistencia, el camino soportado es el plugin con sus quirks, o rc.conf.
