Sandbox de Contenedores:
build → push → run en infraestructura propia

El mismo flujo que ejecuta un pipeline CI/CD de producción — sobre un entorno Docker real y aislado que ya está aprovisionado para ti

Curso: Integración de Soluciones para Plataformas Cloud — Ingeniería de Sistemas
Docente: Ing. Rodolfo Cañas Cervantes · Universidad de la Costa (CUC) · 2026-2
Duración estimada: 90 minutos  ·  Modalidad: terminal web remota (no instalas nada en tu equipo)  ·  Nivel: introductorio
Tipo: actividad práctica calificable — 5% de la nota final de la Unidad 1

OBJETIVOS Qué vas a aprender

Al terminar este laboratorio serás capaz de:

  • Ejecutar el flujo completo de despliegue moderno: build → push → run → verify, igual que un pipeline CI/CD.
  • Construir una imagen de contenedor a partir de un Dockerfile y entender el papel de las capas y la caché.
  • Publicar tu imagen en un registro privado autenticado y comprobar su integridad por digest (sha256:...).
  • Correr tu contenedor como servicio y verificarlo con un health check automatizable (GET /health) — lo mismo que hace un balanceador antes de enviar tráfico real.
  • Trabajar sobre un entorno Docker rootless aislado por estudiante, sin acceso al sistema anfitrión ni a los entornos de tus compañeros.
En la parte teórica vimos cómo se interconectan las nubes (VCN/VPC, peering, VPN). Este lab ejecuta la otra mitad de la historia: cómo una aplicación llega a cualquiera de esas nubes — como imagen portable, no como servidor configurado a mano.

PARTE A Entrar a tu entorno (~10 min)

A.1 — Abrir tu terminal web

Entra a https://labs.proyectoasur.org/ e inicia sesión con tu usuario asignado (tabla de la sección anterior) y la clave cuc2026lab. Nadie más usará tu usuario — si el login te rechaza, revisa que hayas escrito bien tu número. Debe aparecerte un banner como este:

============================================================
 Lab: Sandbox de Contenedores — Integración de Soluciones
 Usuario: ios-est07   |   Tu puerto: 8007   |   Registro: 200.30.0.3:5000
------------------------------------------------------------
 Flujo del lab (guía completa entregada en clase):
   cd ~/hello-multicloud
   docker build -t "$IMAGE" .
   docker login 200.30.0.3:5000          <- usuario y clave del registro
   docker push "$IMAGE"
   docker run -d --name hello -p 8007:3000 "$IMAGE"
   curl localhost:8007/health            <- ESTA ES TU EVIDENCIA
============================================================
Apunta tu puerto del banner: cada estudiante publica su app en un puerto distinto para no chocar con los demás.

A.2 — Verificar tu entorno

whoami
docker version
ls ~/hello-multicloud

Resultado esperado:

  • whoami → tu usuario asignado (ios-estNN).
  • docker version → muestra Client y Server; si Server da error, avisa al docente.
  • El proyecto starter con dos archivos: server.js y Dockerfile.

A.3 — Entender qué vas a desplegar

cat ~/hello-multicloud/server.js
cat ~/hello-multicloud/Dockerfile

Es un servidor HTTP mínimo con un endpoint de salud: GET /health responde JSON {"status":"ok",...} — ese endpoint es tu evidencia final. Cualquier otra ruta devuelve una página de bienvenida. El Dockerfile tiene 4 instrucciones: imagen base oficial (node:22-alpine), directorio de trabajo, copia del código y comando de arranque. Con eso basta para producción en este caso.

PARTE B Construir la imagen (~20 min)

B.1 — Build

cd ~/hello-multicloud
docker build -t "$IMAGE" .

La variable $IMAGE ya viene preconfigurada en tu sesión apuntando a tu propio repositorio dentro del registro del curso (200.30.0.3:5000/hello-multicloud-ios-estNN:v1). Compruébala con echo $IMAGE.

Qué está pasando (léelo una vez, cae en el quiz de U1): Docker descarga la capa base node:22-alpine, copia tu código y congela todo en una imagen inmutable identificada por un digest sha256:.... La segunda vez el build es casi instantáneo: solo se reconstruyen las capas que cambiaron (caché de capas).

B.2 — Verificar la imagen construida

docker images

Debe listar hello-multicloud-ios-estNN con tag v1 y tamaño ~55 MB.

PARTE C Push al registro privado (~15 min)

En producción nadie despliega desde el laptop: la imagen se publica en un registro y desde ahí se corre en cualquier nube. Aquí usamos un registro privado montado para el curso, con autenticación obligatoria.

C.1 — Autenticarte

docker login 200.30.0.3:5000

Usuario: ios-lab (no tu usuario de terminal ios-estNN). Clave: cuc2026lab (la misma de tu terminal). La salida correcta termina en Login Succeeded.

Si te equivocas de usuario/clave tres veces, espera 30 segundos e inténtalo de nuevo — hay protección anti fuerza bruta y te puede bloquear temporalmente.

C.2 — Publicar tu imagen

docker push "$IMAGE"

Salida esperada (captura esto para el entregable):

The push refers to repository [200.30.0.3:5000/hello-multicloud-ios-estNN]
v1: digest: sha256:92907e84d135... size: 856

El digest es la prueba criptográfica de que TU imagen quedó almacenada en el registro.

C.3 — Comprobar que vive en el registro (opcional pero recomendable)

docker rmi "$IMAGE"
docker pull "$IMAGE"
Si puedes borrar tu copia local y re-descargarla desde el registro, la publicación fue perfecta.

PARTE D Correr el contenedor y verificar salud (~15 min)

D.1 — Run

docker run -d --name hello -p ${LAB_PORT}:3000 "$IMAGE"
docker ps
  • -d: en segundo plano (daemonizado).
  • --name hello: nombre fijo para referenciarlo.
  • -p ${LAB_PORT}:3000: publica el puerto interno 3000 del contenedor en tu puerto asignado.

docker ps debe mostrar tu contenedor con status Up ... y el mapeo de puertos.

D.2 — Verificación de salud (LA EVIDENCIA)

curl localhost:${LAB_PORT}/health

Salida esperada:

{"status":"ok","app":"hello-multicloud","hostname":"abd43b2b9b2c","time":"2026-08-22T12:19:04Z"}
Captura de pantalla de este comando con su salida completa. Es el requisito central del entregable: demuestra que un contenedor construido por ti, publicado en un registro y redeployado, está corriendo y respondiendo con un chequeo de salud automatizable — exactamente lo que haría un load balancer o un orquestador antes de enviar tráfico real.

Prueba también la raíz:

curl localhost:${LAB_PORT}/

PARTE E Entregable (~15 min)

Un solo documento (PDF) con estas 4 evidencias, en este orden:

  1. Push al registro: captura de la salida de docker push donde se vea el digest: sha256:....
  2. Contenedor activo: captura de docker ps mostrando hello con Up y el mapeo ${LAB_PORT}:3000.
  3. Chequeo de salud: captura de curl localhost:${LAB_PORT}/health con el JSON completo.
  4. Explicación de 3-5 líneas: ¿por qué el flujo build → push → run es la base de un despliegue multicloud? (Pista: la imagen es inmutable y portable — el mismo digest puede correrse en AWS, Azure, GCP o en un servidor propio; lo único que cambia es dónde está el registro y el runtime.)

Anexo B — El Dockerfile, línea por línea 
FROM node:22-alpine   # imagen base oficial: Node 22 sobre Alpine (~55 MB finales)
WORKDIR /app          # directorio de trabajo DENTRO del contenedor
COPY server.js .      # copia tu código desde el contexto de build hacia /app
EXPOSE 3000           # documenta el puerto que la app escucha
CMD ["node", "server.js"]  # proceso principal del contenedor
Anexo C — server.js completo (la app del starter) 
const http = require("http");
const os = require("os");

const port = process.env.PORT || 3000;

const server = http.createServer((req, res) => {
  if (req.url.startsWith("/health")) {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify({
      status: "ok",
      app: "hello-multicloud",
      hostname: os.hostname(),
      time: new Date().toISOString(),
    }));
    return;
  }
  res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
  res.end("<h1>hello-multicloud</h1><p>Sandbox de contenedores</p>");
});

server.listen(port, () => console.log(`hello-multicloud escuchando en :${port}`));
