Laboratorio 1: Sandbox de contenedores

Construye una imagen, públicala en un registro privado, corre el contenedor y verifica su salud — todo con tu propio Docker, en un entorno aislado que se crea y se destruye contigo

Docente: Ing. Rodolfo Cañas Cervantes Universidad de la Costa (CUC) 2026-2 · Ponderación: por definir

Vas a trabajar con Docker de verdad, no con un simulador. Cada estudiante tiene su propia estación: su propio daemon, su propio registro privado y su propio disco. Nada que construyas lo ve nadie más, y nada sobrevive a la sesión.

El flujo completo es el mismo que usarías en la nube:

  1. Entras a tu estación desde el navegador.
  2. Construyes una imagen de contenedor a partir de un Dockerfile.
  3. La publicas en un registro privado (tu ECR particular).
  4. Corres el contenedor, verificas su healthcheck y su respuesta HTTP.
  5. Ejecutas revisar y la evidencia queda registrada.

El registro es el equivalente al ECR de AWS de la arquitectura que viste en clase: un registro de contenedores donde publicas tus imágenes para poder desplegarlas donde quieras.

A

Parte A — Entra a tu entorno

  1. Entra en https://labs.proyectoasur.org con tus credenciales.
  2. Busca el Lab 1 — Sandbox de contenedores y pulsa Iniciar lab.
  3. Cuando diga Entrar, ábrelo: verás tu terminal en el navegador.

Dentro de tu terminal, comprueba que todo está en orden:

docker version
docker info --format 'driver={{.Driver}}  root={{.DockerRootDir}}'
mi-espacio

El comando mi-espacio copia el código de partida de la aplicación a /workspace/app y te deja ahí. No nada que reservar ni ninguna credencial de registro que teclear: es tu entorno y ya está listo.

Un solo laboratorio a la vez. Tu estación se apaga sola si pasas demasiado tiempo sin trabajar, y al terminar se borra todo: tus imágenes, tus contenedores y tu registro. Lo único que queda es la evidencia que registra revisar.

B

Parte B — Construye la imagen

En /workspace/app hay una pequeña aplicación Node con su Dockerfile. Léelos antes de nada.

B.1 · El código de la aplicación

cat /workspace/app/server.js

B.2 · El Dockerfile

cat /workspace/app/Dockerfile

B.3 · Construye

cd /workspace/app
docker build -t mi-app:1.0.0 .

Comprueba que la imagen quedó en tu Docker:

docker images
B

Fíjate en las capas: cada instrucción del Dockerfile es una capa cacheada. Si cambias solo server.js, el npm install no se vuelve a ejecutar. Ese cacheo es lo que hace rápidos los builds.

C

Parte C — Publica en tu registro privado

Tu registro vive en registry:5000, dentro de tu propia sesión. Es privado: si otro estudiante intenta verlo, le devuelve un catálogo vacío.

C.1 · Etiqueta y publica

docker tag mi-app:1.0.0 $LAB_REGISTRO/mi-app:1.0.0
docker push $LAB_REGISTRO/mi-app:1.0.0

C.2 · Comprueba que se publicó

curl -s http://$LAB_REGISTRO/v2/_catalog
curl -s http://$LAB_REGISTRO/v2/mi-app/tags/list

Deberías ver algo como {"repositories":["mi-app"]} y, al mirar las etiquetas, la versión que acabas de subir.

C.3 · Publica una segunda versión

# cambia algo en server.js y vuelve a construir con otra etiqueta
docker build -t mi-app:2.0.0 .
docker tag  mi-app:2.0.0 $LAB_REGISTRO/mi-app:2.0.0
docker push $LAB_REGISTRO/mi-app:2.0.0
curl -s http://$LAB_REGISTRO/v2/mi-app/tags/list

Confirma que ahora hay dos etiquetas. En el Lab 3 vas a llevar esta misma idea a Docker Hub, con etiquetas inmutables.

D

Parte D — Corre el contenedor y verifica su salud

D.1 · Arranca el contenedor

docker run -d --name mi-app -p 8080:3000 $LAB_REGISTRO/mi-app:1.0.0

D.2 · El healthcheck

El Dockerfile define un HEALTHCHECK que pregunta /salud cada 10 segundos. Docker marca el contenedor como healthy solo si la app responde bien: eso es lo que en producción usarías para que el orquestador reinicie lo que esté roto.

docker inspect -f '{{.State.Health.Status}}' mi-app
docker ps --filter name=mi-app

D.3 · La respuesta HTTP

curl -s http://127.0.0.1:8080/salud
curl -s -i http://127.0.0.1:8080/ | head -5

D.4 · Mira los logs y el estado

docker logs mi-app
docker stats --no-stream mi-app
E

Parte E — Entregable

El entregable es la evidencia registrada por la plataforma. Cuando termines, ejecuta el validador desde tu terminal:

revisar

Comprueba cuatro cosas:

CriterioQué valida
Imagen construidaQue hay una imagen propia, hecha con docker build a partir de tu Dockerfile
Push al registroQue la imagen está publicada en el registro privado de tu sesión
Contenedor sanoQue el contenedor corre y su healthcheck está en verde
Respuesta HTTPQue la aplicación responde 200 con el contenido esperado

Si algo queda en rojo, revisar te dice qué falta y con qué comando arreglarlo.

?

Solución de problemas

SíntomaCausa probableQué hacer
docker build falla con no space left Llenaste el disco de la estación con imágenes intermedias docker system prune -af y vuelve a construir
docker push dice connection refused El registro aún no estaba listo Espera 5 segundos y reintenta; comprueba con curl http://registry:5000/v2/_catalog
El healthcheck nunca pasa a healthy La app no responde en el puerto que espera el Dockerfile El HEALTHCHECK llama al PORT de la app (3000). Mira docker logs mi-app
No puedo ver mi app en el navegador No publicaste el puerto al arrancar el contenedor Arráncalo con -p 8080:3000 y abre la vista web de la sesión
revisar dice que no hay imagen propia La imagen se llama igual que una base (p. ej. node) Etiquétala como mi-app:1.0.0

Checklist antes de entregar

  1. Construiste tu imagen con docker build y la ves en docker images.
  2. La publicaste en tu registro privado y el catálogo la lista.
  3. El contenedor corre y docker inspect dice healthy.
  4. La app responde HTTP 200 en el puerto publicado.
  5. Ejecutaste revisar y los cuatro criterios están en verde.
